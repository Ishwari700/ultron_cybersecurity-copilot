# M11.5 Response Pipeline Audit & Truncation Vulnerability Analysis

**Milestone:** M11.5 — Response Reliability, Long-Answer Delivery & Security Research UX  
**Status:** Complete  
**Date:** 2026-10-08  
**Hardware Profile:** AMD Ryzen 5 5600H (6 cores / 12 threads), 24 GB RAM, NVIDIA RTX 3050 Laptop (4 GB VRAM), Ollama runtime, max concurrent inference = 1.

---

## 1. Executive Summary

This audit inspects the complete end-to-end response delivery path in the Bug Bounty AI platform:
$$\text{Frontend / UI} \longrightarrow \text{FastAPI Routing} \longrightarrow \text{Workspace Service} \longrightarrow \text{Reasoning Engine / Model Adapter} \longrightarrow \text{Ollama Local Inference} \longrightarrow \text{Persistence (SQLite)} \longrightarrow \text{Frontend Rendering}$$

The investigation revealed that the existing architecture suffered from **silent response truncation**, where complex security explanations, vulnerability analyses, and code demonstrations were arbitrarily truncated whenever token limits were reached. The system lacked distinction between intentional termination (`done_reason: stop`) and resource exhaustion (`done_reason: length`), persisting partial responses without warning and rendering them with plain line-wrapping rather than structured, streaming Markdown.

This document identifies all truncation mechanisms, audits context and timeout ceilings, and defines the architectural blueprint for the M11.5 Long Response Subsystem (`src/response/`).

## 3. Audited Parameters & Existing Ceilings

### 3.1 Generation Limits (`num_predict` / `max_tokens`)
* **Conversational Chat (`src/dashboard/service.py`):** Hardcoded to `num_predict = 200`. For any security inquiry requiring more than ~150 words (such as explaining BOLA mechanics, JWT signature bypasses, or deserialization chains), the model was cut off mid-sentence.
* **Reasoning Runner (`src/engine/runner.py`, `src/eval/`):** Hardcoded to `PRIMARY_NUM_PREDICT = 300`.
* **Reasoning Runner Deep Sweep (`src/engine/reasoning_runner.py`):** `num_predict = 512`.
* **Triage Runner (`src/engine/triage_runner.py`):** `num_predict = 256`.

### 3.2 Context Limits (`num_ctx`)
* **Core Configuration (`src/core/config.py`):**
  * `num_ctx_3b = 2048`
  * `num_ctx_7b = 4096`
* **Default Runner Context (`src/engine/runner.py`):** `PRIMARY_NUM_CTX = 2048`.
* **Conversational Context:** The system supplied the last 10 messages from `conversation_messages`. When conversation history grew lengthy, prompts approached or exceeded the 2048-token context boundary, causing Ollama to truncate earlier turns or shift context windows.

### 3.3 Request Timeouts & Ceilings
* **Core Config (`src/core/config.py`):** `request_timeout_seconds = 30.0`.
* **Dashboard Service (`src/dashboard/service.py`):** `timeout_seconds = 25.0` on LLM generation calls.
* **HTTP Transport (`src/engine/runner.py`):** Strict wall-clock ceiling with a 500ms teardown tolerance (`effective_timeout + 0.5s`), forcibly closing client sockets on expiration.
* **Timeout Behavior:** In `src/dashboard/service.py`, if generation exceeded 25 seconds, an exception was caught and silently converted into a static fallback message (`"Hello..."` or `"I am Bug Bounty AI..."`), discarding all generated content.

## 4. Root Causes of Silent Truncation

1. **Conflation of `stop` and `length` Termination:**
   Ollama returns metadata in each generation response:
   * `done: true`
   * `done_reason: "stop"` (Model reached end of sequence / naturally completed)
   * `done_reason: "length"` (Generation abruptly halted due to `num_predict` limit)
   The existing dashboard handler inspected only `text = resp.get("response", "").strip()` and ignored `done_reason`. Consequently, responses truncated mid-code block or mid-word were treated as completely finished.

2. **Absence of Continuation Protocol:**
   When `done_reason == "length"` occurred, there was no continuation subsystem to request the remainder of the response. The truncated text was treated as the full response.

3. **All-or-Nothing Synchronous HTTP Requests:**
   The dashboard UI relied on synchronous HTTP requests (`fetch('/api/investigations/.../messages')`). The client received nothing until the entire generation completed or timed out. If a timeout occurred, the partial output was discarded.

4. **Monolithic Message Persistence:**
   The `conversation_messages` table stored only a single `content` string. It did not support multi-chunk responses, chunk provenance, sequence tracking, or partial states (`GENERATING`, `CONTINUING`, `TOKEN_LIMIT`, `USER_STOPPED`).

5. **Frontend Rendering Bottlenecks:**
   In `frontend/src/components/ConversationView.tsx`:
   * Text was displayed via a plain `<div>` with CSS `whiteSpace: 'pre-line'`.
   * Markdown headers (`#`, `##`), bullet lists (`-`, `*`), and tables were rendered as raw unformatted plaintext.
   * Fenced code blocks (```python ... ```) were not parsed, highlighted, or wrapped in copy containers.
   * Long unbroken strings (e.g., URLs, stack traces, hex dumps) risked overflowing container widths without explicit CSS `overflow-wrap: break-word`.
   * No controls existed for copying sections, exporting as Markdown/TXT, searching within the response, or collapsing lengthy technical sections.

## 5. Architectural Recommendations for M11.5

### 5.1 Recommended Internal Chunk Size & Context Profile
Given the local hardware constraints (Ryzen 5 5600H, 24 GB RAM, RTX 3050 Laptop 4GB VRAM running Qwen 2.5 Coder 3B / 7B with max concurrent inference = 1):
* **Internal Chunk Size (`CHUNK_NUM_PREDICT`):** **512 tokens** per chunk.
  * *Rationale:* 512 tokens generates in ~3.5 to 5.0 seconds on the RTX 3050. This provides responsive progressive streaming while remaining well within HTTP timeout boundaries (30s).
* **Context Ceiling (`CHUNK_NUM_CTX`):** **4096 tokens**.
  * *Rationale:* 4096 fits comfortably within 4GB VRAM for Qwen 2.5 Coder 3B/7B (Q4_K_M quant) and accommodates the base prompt, bounded conversation history, and continuation context.
* **Safety Ceilings:**
  * `MAX_CONTINUATION_CHUNKS = 8` (allowing up to $8 \times 512 = 4,096$ tokens total generated output per assistant turn).
  * `MAX_CUMULATIVE_TOKENS = 4096 tokens`.
  * `MAX_CONTEXT_REPACKING_ATTEMPTS = 3`.
  * `CHUNK_TIMEOUT_SECONDS = 30.0s`.

### 5.2 Multi-Signal Completeness Detection
A response must never be assumed complete merely because text generation ceased. The new subsystem (`src/response/completeness.py`) evaluates multiple structural signals:
1. **Model Stop Reason:** `done_reason == "stop"` vs `done_reason == "length"`.
2. **Code Fence Balance:** Odd count of triple backticks (` ``` `) indicates an unclosed code block.
3. **Markdown Syntax Incompletion:** Dangling markdown header indicators (`#`), unfinished markdown tables (row lacking trailing `|`), or incomplete bold/italic formatting.
4. **List Structure:** Trailing unfinished numbered list (`\n3. `) or bullet list item (`\n- `).
5. **JSON/XML Structure:** Unbalanced curly braces `{`, brackets `[`, or tags `<tag>`.
6. **Sentence Termination:** Trailing dangling punctuation (e.g. colon `:`, ellipsis `...`, hyphen `-`, or mid-word alphanumeric characters without terminal punctuation).

The detector outputs:
* `COMPLETE`: High confidence natural termination.
* `LIKELY_COMPLETE`: Stop reason is stop, balanced structures, mild punctuation variance.
* `LIKELY_INCOMPLETE`: Stop reason is length or dangling punctuation with balanced structures.
* `INCOMPLETE`: Token limit reached with unbalanced code fences, dangling headers, or mid-sentence cut-off.
* `UNKNOWN`: Insufficient evidence.

### 5.3 Deterministic Continuation & Overlap Protection
When an incomplete chunk is detected:
1. The engine retains the accumulated text.
2. It frames a specialized continuation prompt containing the trailing context (~150-250 tokens) and an instruction:
   `"Continue the analysis directly from the exact interruption point. Do not repeat prior content. Do not output meta-commentary."`
3. Upon receiving the continuation chunk, the engine runs **overlap detection** (`src/response/merger.py`):
   * Exact suffix-prefix string matching.
   * Normalized whitespace & punctuation matching.
   * Sentence-level overlap elimination (if the model re-states the trailing sentence before proceeding).
4. The cleaned chunk is merged seamlessly into the canonical response session.

### 5.4 Response Persistence & Data Model
A dedicated response persistence schema will store:
* **`response_sessions`**: Session ID, investigation ID, parent message ID, model name, status, termination reason, cumulative tokens, timing.
* **`response_chunks`**: Chunk ID, session ID, sequence index, raw content, normalized content, token count, stop reason, execution latency, SHA-256 content hash.
* **`response_versions`**: Support for regeneration and version inspection without overwriting historical turns.

## 6. Security Invariant Compliance (R1–R18)

| Requirement | Invariant Guard | Implementation Mechanism |
|---|---|---|
| **R1** | Partial output cannot become verified finding | Epistemic state machine requires explicit human verification; raw responses are strictly marked unverified data. |
| **R2** | Response continuation cannot expand scope | Continuation prompts inherit bounded target context; no scope policy mutation allowed. |
| **R3** | Continuation cannot override system policy | System security instructions are prepended to every continuation chunk request. |
| **R4** | Previous output is DATA, not AUTHORITY | Model output cannot execute tools or alter state without human confirmation. |
| **R5** | Continuation cannot alter AuthorizationRecord | Authorization status is cryptographically signed and stored in immutable ledger tables. |
| **R6** | Frontend cannot execute arbitrary HTML/JS | React rendering uses strict DOM text nodes and sanitization; no raw `dangerouslySetInnerHTML`. |
| **R7/R8** | Redaction applied to stored/downloaded content | `CredentialVault.redact_text` is enforced on all chunks before storage, export, or rendering. |
| **R12** | Deterministic user cancellation | Cancellation tokens terminate HTTP requests and record `USER_STOPPED` status immediately. |
| **R13** | Token limit cannot be marked COMPLETED | `done_reason == "length"` transitions status to `TOKEN_LIMIT` or `CONTINUING`, never `COMPLETED`. |
| **R14** | Finite bounds on continuation | Enforced hard caps: max 8 chunks, max 4096 tokens, max 3 repacking attempts. |
| **R15** | Overlap prevention | Deterministic suffix-prefix alignment prevents duplicate sentences. |
| **R16** | Provenance preservation | Every chunk records chunk ID, sequence number, hash, and stop reason. |

## 7. Audit Conclusion & Next Steps

The response pipeline audit confirms that silent truncation is caused by rigid `num_predict` caps (200-300 tokens), lack of `done_reason` discrimination, absence of continuation loops, and plain text rendering in the frontend.

With this audit established, implementation proceeds immediately to **Phase 11.5.2: Long Response Engine (`src/response/`)**.
